# 🍽️ Dinner Decider

**Dinner Decider** is a self-hosted app that ends the nightly "what's for dinner?" argument. Every
day an AI agent proposes three dinners tailored to your household — diets, allergies, what you've
eaten recently, which cuisines you actually like, and what's in season — and everyone votes. The
winner is recorded, your tastes are learned over time, and you can plan the week, build a shopping
list, save favourites, and add your own recipes.

It runs entirely on your own machine: a FastAPI backend, a React frontend, a local SQLite database,
and Google Gemini for the suggestions. One household per deployment.

---

## ✨ Features

- **Daily AI suggestions** — 3 dinners generated by a Google ADK + Gemini agent that searches the
  web for real recipes and YouTube videos.
- **Household voting** — one vote per person per day; live results with progress bars.
- **Learns your tastes** — winning and highly-rated cuisines nudge per-person preference scores.
- **Dietary safety, enforced server-side** — if anyone is vegetarian, every option is veg or has a
  veg alternative; declared allergies are screened against ingredients (not left to the prompt).
- **Never an empty page** — if the AI returns bad output or is unavailable, suggestions fall back
  to your last good day, then to a built-in seed menu.
- **Weekly meal plan** — pin any meal to any day, overriding the AI.
- **Shopping list** — aggregate and de-duplicate ingredients across the planned week.
- **Favourites & "cook again"** — your top-rated meals, one tap to re-plan them.
- **Leftovers night** — mark a day as no-cook; it's recorded and skips preference learning.
- **Your own recipes** — add meals to the pool and plan them like any AI suggestion.
- **Optional notifications** — ping an ntfy/webhook when the daily suggestions land.
- **Lightweight auth** — a shared household passcode + signed session; identity for votes/ratings
  comes from the session, never the request body.

## 🏗️ Architecture

| Layer | Stack |
|-------|-------|
| **Frontend** | React 19, Vite, TypeScript, Tailwind CSS v4, Framer Motion, lucide-react. Routes are code-split; the recipe drawer, weekly plan, and recipe box are lazy-loaded. |
| **Backend** | FastAPI, SQLAlchemy 2, APScheduler (daily jobs), Alembic (migrations), Starlette signed-cookie sessions. |
| **Database** | SQLite with WAL mode (safe concurrent reads while the scheduler writes). |
| **AI** | Google ADK (Agent Development Kit) driving Gemini, with a delegated `google_search` sub-agent. |

### The AI agent

A main agent orchestrates suggestions using these tools:

- `google_search` (via a sub-agent) — finds real recipes and YouTube videos.
- `get_meal_history` — avoids repeating a meal within ~7 days.
- `get_user_preferences` — favours cuisines the household rates highly.
- `get_current_season` — leans into seasonal ingredients.

Its raw output is treated as **untrusted**: it is parsed defensively (with retries on bad JSON),
validated against a schema, and run through the server-side dietary/allergy filter before anything
is saved.

---

## 🔄 The daily lifecycle

1. **Generate (default 5:00 PM, your timezone)** — the scheduler runs the agent, validates and
   filters the result, and saves 3 suggestions. On failure it falls back to last-known-good, then a
   seed menu, and **never wipes** the current suggestions unless it has a valid replacement. If a
   notification webhook is configured, it pings it.
2. **Vote** — members pick their name, view recipes (with veg alternatives), and vote. One vote per
   person per day, changeable until finalization.
3. **Finalize (11:59 PM)** — tally votes, record the winner in history, and bump the winning
   cuisine's preference score for everyone who voted for it. Rating a meal 4★+ later boosts it
   further; ≤2★ lowers it. A day marked **leftovers** is left untouched.

## 🚀 Deploy

### Option A — Docker (recommended)

```bash
git clone https://github.com/samyak1901/dinner-decider.git
cd dinner-decider
cp .env.example .env          # then edit .env (see Configuration below)
docker compose up -d --build
```

The API is served at `http://localhost:8000`. The database is persisted to `./data/` on the host.
Migrations run automatically on startup. Build and serve the frontend separately (see below) or
point your own static host at `frontend/dist`.

### Option B — Manual

**Backend** (needs [uv](https://docs.astral.sh/uv/) and Python 3.11+):

```bash
cp .env.example .env          # edit it
uv sync
uv run uvicorn backend.main:app --host 0.0.0.0 --port 8000
```

**Frontend** (Node 20+):

```bash
cd frontend
npm install
npm run dev -- --host         # dev server on :5173, proxies /api → :8000
# or: npm run build            # production bundle in frontend/dist
```

Open **http://localhost:5173**.

### Sharing on your LAN

Run both servers with `--host`, then add your machine's address to `CORS_ORIGINS` in `.env`
(e.g. `http://192.168.1.15:5173`) and restart the backend. Household members open
`http://192.168.1.15:5173`.

## ⚙️ Configuration

All settings come from environment variables / `.env` (see `.env.example`):

| Variable | Default | Purpose |
|----------|---------|---------|
| `GOOGLE_API_KEY` | — | Gemini API key. Without it, suggestions use the seed-menu fallback. |
| `GEMINI_MODEL` | `gemini-2.5-flash` | Model used by the agent. |
| `DATABASE_URL` | `sqlite:///./dinner_decider.db` | SQLite path (Docker uses `/app/data`). |
| `SCHEDULER_HOUR` | `17` | Hour (0–23) to generate suggestions, in `TIMEZONE`. |
| `TIMEZONE` | `UTC` | IANA timezone for the scheduler, e.g. `Australia/Sydney`. |
| `CORS_ORIGINS` | `http://localhost:5173` | Comma-separated allowed frontend origins. |
| `HOUSEHOLD_PASSCODE` | _(empty)_ | Shared passcode gating the app. **Empty = open mode (no login)** — fine for local use; set it before exposing the app. |
| `SESSION_SECRET` | _(empty)_ | Key signing session cookies. Empty = ephemeral key (logins reset on restart); set a long random value to keep logins across restarts. |
| `NOTIFY_WEBHOOK_URL` | _(empty)_ | Optional webhook (e.g. an `https://ntfy.sh/<topic>` URL) pinged when suggestions are generated. |

> **Security note:** with `HOUSEHOLD_PASSCODE` unset the app runs in *open mode* with no
> authentication — convenient locally, but set a passcode (and a `SESSION_SECRET`) for any
> deployment others can reach.

## 📖 Using the app

1. **Settings** — add household members (name, vegetarian flag, dietary restrictions like
   `no peanuts` or `halal`).
2. **Today** — pick your name, then **New Suggestions** to generate (or wait for the daily run).
   Vote, open the recipe drawer for ingredients/steps/video, or hit **Leftovers tonight**.
3. **Plan** — pin meals to days for the week, generate a **shopping list**, and re-cook
   **favourites**.
4. **Recipes** — add your own meals to the pool so they can be suggested or pinned.
5. **History** — browse past winners and rate them; ratings feed back into preferences.

If a passcode is set, you'll log in once per device; a logout button appears in the nav.

---

## 💾 Data model

A local SQLite database (path set by `DATABASE_URL`):

- **`users`** — household members and dietary info.
- **`meals`** — every recipe ever suggested or manually added (the pool).
- **`daily_suggestions`** — today's 3 candidates.
- **`votes`** — who voted for what, today.
- **`meal_history`** — finalized winners with ratings/notes (a "leftovers" day has no winner).
- **`preferences`** — per-user, per-cuisine scores (0.0–1.0).
- **`planned_meals`** — manual pins/overrides for specific dates.

Schema changes are managed with **Alembic** (`alembic upgrade head` runs on startup).

## 🔌 API overview

All `/api/*` routes (except `/api/health` and `/api/auth/*`) require a session when a passcode is
set. Key endpoints:

- `POST /api/auth/login` · `POST /api/auth/logout` · `GET /api/auth/me` · `POST /api/auth/select-user`
- `GET /api/suggestions/today` · `POST /api/suggestions/refresh`
- `POST /api/votes` · `GET /api/votes/today`
- `GET /api/history` · `POST /api/history/{date}/rate` · `POST /api/history/{date}/leftovers`
- `GET/POST /api/users`
- `GET/POST /api/meals` · `GET /api/meals/favourites`
- `GET /api/plan/week` · `PUT/DELETE /api/plan/{date}` · `POST /api/plan/shopping-list`

Interactive docs are available at `http://localhost:8000/docs` while the backend is running.
